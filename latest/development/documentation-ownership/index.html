    Documentation ownership and source boundaries¶

    This guide is for contributors changing documentation or extracting a component from the Core repository. Read the architecture rules and documentation layout first.

    It records the source boundaries for #605 under the documentation extraction epic. Ownership below is the target responsibility; all inventoried paths currently live in OpenTLV/opentlv. No page, example or publishing job moves in this step. The standalone portal is not yet the replacement for the existing pipeline.

    Ownership rules¶

    Owner Canonical responsibility
    Core (OpenTLV/opentlv) C and C++ APIs, shared semantics, architecture, Reader, Writer, Document, Query, Schema, Codec, built-in formats and standards, native examples, source comments, Core build and development instructions
    Binding Its public API, installation, ownership and lifetimes, idiomatic usage, supported features, dependency declarations, tests and executable examples
    Tool Its commands, options, input/output conventions, installation, tests and executable examples
    Portal (OpenTLV/opentlv-docs) Global navigation, presentation, shared assets, MkDocs configuration, assembly, version selection, integration of generated references and examples, site validation and publication

    C++ remains part of Core. Rust, Python and Lua documentation will move with their implementations to OpenTLV/opentlv-rust, OpenTLV/opentlv-python and OpenTLV/opentlv-lua; CLI documentation will move to OpenTLV/opentlv-cli. Go and WebAssembly follow the same component ownership rule; their destination repository names must be recorded when their extraction is scheduled. These destinations are ownership assignments, not claims that a migration is complete.

    Each fact has one canonical source. A portal build may assemble content from an owning repository into disposable build output; it must not maintain an edited copy of that content. Generated C/C++ references come from the selected Core revision. Binding compatibility, feature coverage and tested examples are separate facts supplied by the component, not inferred from Core support.

    Core changes update Core documentation in the same change. They do not require unrelated binding changes, a checkout of the portal, or successful portal publication. Binding and tool releases remain independent of Core releases.

    Transitional exceptions¶

    The inventory uses these dispositions. They describe follow-up work, not additional repositories or new documentation formats.

    Code Current location and responsibility Exit condition
    Keep Core owns and maintains this source in Core No extraction is required; the portal consumes the source
    Component Binding/tool owners maintain their documentation here while their implementation remains here Move source documentation and examples with that component, update inbound links and checks, then remove the old canonical content
    Portal Portal-owned content or infrastructure is temporarily hosted in Core Move it after the independent pipeline preserves its behavior and passes validation; update links and remove the obsolete Core copy/job
    Mixed Core retains its contracts; embedded component content or portal instructions have temporary co-location Separate the identified parts when their owner migrates, preserve anchors/links, and retain the Core source without copying its contracts into the portal

    For a mixed page, ownership applies to sections and examples as well as files:

    • Core owns the C execution contract, C++ facade, native build options and C/C++ examples. Binding owners own language-specific snippets and their source tests; tool owners own command examples and output contracts.
    • The binding matrix in concepts/bindings.md currently combines Core adaptation rules with component feature evidence. Core retains the rules. Components own their feature evidence; the portal will present the cross-component matrix.
    • formats/support.md retains native C/C++ support in Core. CLI identifiers and language preset availability follow their components; their combined presentation belongs to the portal.
    • guides/examples.md retains native example coverage in Core. Binding example inventories follow their components; the combined index belongs to the portal.
    • Core guides and Getting Started retain shared explanations and C/C++ usage. Existing binding tabs stay synchronized with the current binding sources until component extraction. Later portal assembly integrates tested examples from their owners; implementing that mechanism is outside #605.
    • development/workflow.md and the Query verification pages retain Core checks and evidence. Binding/CLI checks follow their owners; future ecosystem compatibility orchestration must not become a Core release prerequisite.
    • Documentation layout and audit pages retain Core contribution rules and the historical audit record. Site presentation, global navigation, mike deployment instructions and cross-component conventions follow the portal.

    Temporary co-location does not transfer ownership. Existing monorepository checks still run during the transition. They must be separated by responsibility as the affected components move; do not silently skip missing sources or retain mandatory consumer checkouts in Core CI.

    Links crossing future repository boundaries¶

    These links are mostly repository-relative today. They become cross-repository links as owners migrate; preserve the relationship and fragment, not an assumed single-repository base URL.

    Current source / link family Target and migration responsibility
    Core guides and getting-started/README.md: language tabs, <!-- example: PATH --> markers and runnable-example links bindings/*/examples/ and language guides: binding owns source/tests; Portal integrates selected examples without requiring binding updates for a Core-only documentation change
    concepts/bindings.md, formats/support.md, guides/examples.md Binding sources/tests, CLI registrations and examples: retain Core facts locally; move component facts with their sources and preserve portal navigation
    reference/c-api.md, reference/cxx-api.md, format guides and native examples tlv/include/, tlv++/include/, examples/: keep Core-relative source links in canonical Markdown; assembled links must target the selected Core revision
    docs/README.md, root/component README files and CONTRIBUTING.md Core pages and the unified landing page: preserve a Core entry point, update portal destinations and keep existing anchors where practical
    Doxygen @docs links, OPENTLV_DOCS_URL in cmake/doxygen.cmake, C++ tag-file references and reference entry pages Hand-written guides and sibling C/C++ HTML trees: preserve both directions when generation and publication are separated
    playground/index.md, its JavaScript and development/webassembly.md WebAssembly distribution/API and browser assets: component produces the module; Portal owns its selected-version integration
    mkdocs.yml (repo_url, edit_uri, site_url), tools/docs/hooks.py (REPO_URL, REF) and theme links Current single-repository source/edit/version assumptions, including legacy marekcingel/OpenTLV URLs: portal migration must select the owning repository and revision for each source
    development/workflow.md, documentation layout, CONTRIBUTING.md and .github/workflows/docs.yml Build/publishing commands, artifacts and deployment destinations: update together after the replacement pipeline is validated

    Keep published page paths and heading anchors where practical. Before moving a source, find inbound links in docs, headers, component READMEs and contributor files. Record changed paths and redirects where needed; do not remove content because the current portal does not yet consume it. A successful site build does not prove remote links or their release-specific fragments exist.

    Source contract for the standalone portal¶

    Core supplies its maintained Markdown, relative assets, native example sources, public headers and independent API generation targets from a selected Git tag or commit SHA. The portal must record the resolved revision and consume those sources without modifying the Core checkout or requiring optional consumers for Core-only documentation. Local multi-root development may use the sibling Core checkout, but must distinguish local changes from a reproducible release build.

    Preserve relative page paths and anchors in assembled Core content. Resolve source and edit links against that page's owning repository and selected revision, including links outside docs/. Keep generated C and C++ references from the same Core revision and preserve their sibling layout and cross-links. Use the existing MkDocs Material rendering conventions for current pages.

    The current tree still contains the explicit Component, Portal and Mixed exceptions above; it is not a finished Core-only export. Their inventory tells the extraction work which sources to retain, separate or move. This issue does not define an assembly engine, component version manifest, compatibility service or new publication workflow. Those belong to subsequent epic work. Remove the old portal infrastructure only after its replacement has been validated.

    Documenting new Core functionality¶

    1. Update public C/C++ declarations and Doxygen comments with the implementation.
    2. Update the canonical Core contract, relevant guide and native executable examples. Follow the layout conventions; keep component-specific behavior in the owning component's documentation.
    3. Add or update the ownership inventory row for changed source boundaries. For a temporary exception, record its owner, the retained location and the migration condition rather than introducing a second canonical copy.
    4. Update native support/build/example inventories when applicable. A Core-only change does not imply binding parity and must not fabricate binding examples or require unrelated binding implementation changes.
    5. Run the relevant source/example inventory checks and Markdown lint. During this transition also follow the existing strict-site validation instructions; when the portal moves, site assembly/publication checks belong to its CI, while Core retains checks of its own sources and API generation.

    Continue with the contribution workflow for commands and the extraction epic for migration sequencing and preservation requirements.
